# backend/seeding (신규 모듈, D3)

루트 문서를 먼저 읽는다: `/CLAUDE.md`, `docs/architecture.md` 3절(프리시딩 흐름), `docs/data-model.md`(`seeding_jobs`).

## 책임

- 지도 생성 시 해당 지역을 프리시딩 큐에 넣는 워커 (트리거는 `maps` 모듈이 호출)
- 데모/발표 대상 지역 1~2곳에 대한 수동 선점 배치 잡
- 큐에 있는 잡을 소비해 `places`(수집) → `llm`(라벨링) 파이프라인을 돌리고 `place_facts`를 채움

## 왜 이 모듈이 존재하는가

기획안 5-8의 온디맨드 라벨링은 첫 추천 요청에 후보 전체(예 18곳)×LLM 호출이 대기시간에 얹히는 문제가 있다(멘토 피드백). 5-4의 수동 트리거+임계값이 만드는 자연 지연 동안 미리 채워두면 실제 추천 시점엔 대부분 캐시 히트가 된다. `docs/architecture.md` 3절의 타임라인 다이어그램을 그대로 구현한다.

## 넘지 말 것

- 이 모듈은 **오케스트레이션만** 한다. 실제 수집은 `places`, 실제 라벨링(모델 호출 ③-a-1)은 `llm`을 호출한다 — 여기서 직접 LLM을 부르지 않는다.
- 못 채운 값의 처리(제거/통과)는 이 모듈이 정하지 않는다. `docs/constraints.md`의 `unknown_policy`를 소비하는 건 `recommend` 모듈이다.

## 완료 정의

- `seeding_jobs` 큐 소비 워커 + 단위 테스트(잡 상태 전이 known 케이스)
- 지도 생성 → 잡 큐잉 → 워커 소비까지의 통합 시나리오는 루트가 통합 테스트로 검증하므로, 이 모듈은 워커 단위 테스트까지만 책임진다
