# 기술 아키텍처

작성 기준: `최종기획안.md` + 기술 멘토링 피드백(2026-09-02)
정본 관계: 이 문서가 모듈 경계·데이터 흐름의 정본이다. API 계약 자체는 `api-spec.yaml`을 본다.

멘토 피드백 핵심 2가지가 이 문서의 축이다.
1. "어떤 API를 쓸지"가 아니라 **우리 서버·DB를 두고 거기서 한 번 추상화**한다 — API 선택에 제약을 두지 않는다.
2. 장소 서비스는 **데이터가 전부**다. 라벨링(=우리가 만든 1차 데이터)이 곧 해자다.

## 1. 모듈 경계

각 모듈이 서브 디렉토리 Claude Code 1개의 작업 범위(`backend/<module>/`)가 된다. 모듈은 자신의 DB 테이블만 직접 쓰고, 다른 모듈의 데이터는 반드시 그 모듈이 정의한 API/함수 계약을 통해서만 읽는다.

모듈은 두 층으로 나뉜다. **수평 레이어**는 모든 기능 모듈이 공통으로 딛고 서는 바닥이고, **기능 모듈**은 그 위에서 각자의 도메인을 담당한다.

### 수평 레이어 (어느 모듈이든 직접 import한다)

| 모듈 | 책임 | 기획안 근거 | 의존 |
|---|---|---|---|
| `common` | 에러 포맷, 설정, DB 세션·트랜잭션 경계, `seq` 채번, 좌표 유틸(PostGIS), `event_log` 발행 계약(`record_event`) | #2 | — |
| `auth` | 카카오 OAuth 콜백, 세션 쿠키 발급·검증, 로그인/로그아웃/탈퇴 | 13절, 12절 | `common` |
| `authz` | 롤 → 접근범위 + 액션 선언적 권한 판정, 라우터 의존성(`guard`)으로 404/403 분기, 응답에 `permissions` 주입 | 15-1 (재설계) | `common`, `maps` |

`authz`가 `maps`를 의존하는 것은 멤버십 조회(`maps.api.DbMembershipGateway`) 때문이다. 수평 레이어 안에서 유일하게 기능 모듈을 향하는 화살표라, 이 방향이 늘어나면 순환이 생길 수 있어 주의해서 본다.

아래 `의존` 열에는 **수평 레이어를 적지 않는다.** 전부 쓰는 것이 전제이기 때문이다.

| `shortlist` | 확정 리스트 추가/제외, 동선 계산(모델 미사용) | 5-3, 5-10 | `pins` |
| `realtime` | SSE 채널(전체/개인), `event_log` 폴링·재동기화 | 5-5-1 | — |

`의존` 열은 실제 import를 기준으로 적는다(2026-09-23 기준, #113). 계획상 필요할 것 같은 의존을 미리 적지 않는다 — 표와 코드가 어긋나면 표를 믿을 수 없게 된다.

의존 방향은 위에서 아래로만 흐르게 한다. `pins`가 `recommend`를 참조하지 않는다(추천이 핀을 만들지만 핀이 추천을 알 필요는 없다).
예외였던 `realtime`의 역방향 의존(전 모듈→realtime)은 이벤트 계약을 `common`으로 내려서
없앴다 — 이제 화살표는 전부 아래로만 흐른다. 각 모듈은 `common.events.record_event(db, event)`
로 쓰고, `realtime`은 `event_log`를 읽기만 한다.

## 1.1 기능 실행 함수(flow) — 언제, 어디에 두는가

한 요청이 **두 모듈 이상의 테이블**을 같은 커밋 안에서 바꾸면 그 모듈이 `flows.py`에 기능
실행 함수를 만든다. 한 모듈의 테이블만 바꾸면 기존 `service.py`가 그대로 처리한다.

기능 실행 함수는 **`docs/api-spec.yaml`에서 그 엔드포인트의 태그가 가리키는 모듈**에 둔다 —
별도의 `usecases/` 공유 디렉토리를 만들지 않는다. 6개 세션이 각자 디렉토리에서 병렬로 작업하는
이 팀의 구조상, 아무도 소유하지 않는 공유 디렉토리는 모든 교차 기능의 병목이 된다.

지금 flow가 필요한 것은 둘뿐이다:

| flow | 엔드포인트 | 위치 |
|---|---|---|
| 후보 게시 | `POST /candidates/{candidateId}/publish` | `backend/recommend/flows.py::publish_candidate` |
| 핀 확정 | `POST /maps/{mapId}/shortlist` | `backend/shortlist/flows.py::confirm_pin` |

**flow 함수 자체는 순서와 실패 처리만 담당한다 — 판단 로직은 두지 않는다.** 판단은 각 모듈의
`core.py` 순수 함수에 있다(`docs/code-quality.md`). flow에 `if`가 늘어나기 시작하면 그 분기는
core.py로 옮긴다.

**flow가 필요 없는 것들** (기존 `service.py`가 그대로 처리):

| 작업 | 바뀌는 테이블 |
|---|---|
| 핀 CRUD, 반응 등록/삭제 | `pins` + `event_log` |
| 확정 리스트 순서 변경 | `shortlist_items`만 |
| 동선 계산 | 계산 결과 + `event_log` |
| 근거 추가/토글, 추천 실행 생성 | `recommend` 테이블 + `event_log` |
| 초대 수락 | `memberships` + `event_log` |

`event_log`는 "다른 모듈의 테이블"로 세지 않는다 — 모든 모듈이 `common.events.record_event`로
쓰도록 설계됐기 때문이다(§4.1). 그렇지 않으면 사실상 모든 쓰기가 flow가 되어 이 구분 자체가
무의미해진다.

### 모듈 간 import 규칙 (2026-09-23 개정, #113)

무엇을 가져오느냐에 따라 허용 범위가 다르다. 이전 규칙은 "교차 모듈은 전부 `api.py` 경유"였는데,
실제 import 36건 중 그 경로를 쓰는 것이 2건뿐이었다. 나머지 34건 중 33건은 정상 동작인데
규칙이 그 경우를 다루지 않아 형식상 위반으로 보였다. 규칙 쪽을 현실에 맞춘다.

| 가져오는 것 | 허용 | 이유 |
|---|---|---|
| 수평 레이어(`common`, `auth`, `authz`) | 어느 모듈이든 직접 | 모든 모듈이 딛는 바닥이다. 앞에 `api.py`를 하나 더 두면 간접 계층만 늘고 줄어드는 관리 포인트가 없다 |
| 다른 모듈의 `schemas.py` | 직접 | 응답 타입 공유다. 데이터를 읽는 게 아니다. 예: `shortlist`의 응답 안에 `pins.schemas.Pin`이 들어간다 |
| 다른 모듈의 **데이터 조회·변경** | `<module>/api.py`만 | 예: `recommend/flows.py`가 `pins.api.create_ai_pin(...)`을 부른다 |
| 다른 모듈의 `models.py` | **금지** | DB 테이블이다. 소유 모듈 밖에서 직접 다루면 스키마 변경이 어디까지 번지는지 알 수 없어진다 |
| 다른 모듈의 `service.py` | **금지** | 공개 접점이 아니다. 필요하면 그 모듈이 `api.py`에 함수를 연다 |

`api.py`가 없는 모듈은 아직 다른 모듈에게 열어줄 데이터가 없다는 뜻이다. 필요해지는 쪽이
그 모듈 담당에게 요청해서 만든다(`maps/for_Root.md`, `auth/for_Root.md`가 그렇게 요청한 전례).

## 1.2 엔드투엔드 흐름 예시 — 후보 게시

지금까지 이 문서에 모듈을 가로지르는 실행 흐름이 없었다(멘토 리뷰 지적). 가장 복잡한 흐름
하나를 예로 남긴다 — 나머지 흐름은 `docs/api-spec.yaml`과 각 모듈 `flows.py`/`service.py`를
따라가면 같은 패턴이다.

```
클라이언트 ─POST /candidates/{id}/publish→ recommend/router.py (HTTP 셸)
   → recommend/flows.py::publish_candidate           ← 순서·트랜잭션 담당, 판단 없음
       1. recommend/service.py  후보·run 조회                              (404)
       2. recommend/core.py::check_publishable(...)  순수 판정             (409/403)
       3. pins.api.create_ai_pin(db, ...)             INSERT pins          (커밋 안 함)
       4. recommend/service.py  UPDATE candidates.published_pin_id        (커밋 안 함)
       5. common.events.record_event(db, pin_published_event(pin))        (커밋 안 함)
   ← 반환
   common/database.py::get_db  ── COMMIT (요청당 이 한 곳뿐) ──→ pins·candidates·event_log 동시 확정
   realtime/dispatcher.py  event_log 폴링 → 전체 채널 SSE
```

실패하면 1~5 전부 롤백된다 — pins 행만 생기고 이벤트는 안 나가는 상태는 구조적으로 불가능하다
(§4.1).

## 1.3 모델 변경과 상주 상태 (2026-09-23 정리, #115)

멘토 리뷰(PR #94): "가장 중요한 건 비즈니스 로직과 모델 변경 로직을 어떻게 볼 것인지", "서버
내에서 상주하는 상태를 관리해야 하는 부분은 없는지, 있다면 이 상태의 변경·접근 흐름을 코드
레벨에서 어떻게 제어할 것인지."

계층 구분은 `docs/code-quality.md`(기능형 코어/명령형 셸)와 §1.1(flow)에 나뉘어 있다. 여기서는
"데이터를 실제로 바꾸는 코드가 어디 있는가"만 한 곳에 모은다.

### 모델 변경이 일어나는 곳

| 계층 | 하는 일 | DB를 아는가 |
|---|---|---|
| `core.py` | 판단과 계산. 순수 함수 | 모른다 |
| `service.py` | 한 모듈 안의 데이터 변경 | 안다 (`db: Session`을 받는다) |
| `flows.py` | 여러 모듈에 걸친 변경의 순서와 실패 처리 | 안다. 단 판단은 하지 않는다(§1.1) |
| `common/database.py::session_scope` | 커밋과 롤백 | 여기가 유일한 커밋 지점이다 |

`service.py`와 `flows.py`가 `db: Session`을 직접 받고 SQLAlchemy를 쓴다. 저장소(repository)
계층은 아직 없다. 지금 판단으로는 모듈당 쿼리가 2건에서 9건 규모라 계층을 하나 더 얹어
줄어드는 관리 포인트가 보이지 않고, DB를 갈아탈 계획도 없다(PostGIS의 `geography`와 `ST_`
함수에 묶여 있다). 연결과 생애주기는 이미 `get_db_session`과 `session_scope`가 감추고 있어서,
소비자가 커넥션을 열거나 커밋 시점을 정하는 일은 없다.

**이건 아직 팀이 확정한 결정이 아니다.** PR #118에서 받은 멘토 답변은 반대 방향이다. 연결
풀을 관리하는 DB 서비스를 앱 런타임 동안 하나인 객체로 두고, 기능 모듈에는 세션보다 한 번 더
추상화된 핸들(Unit of Work나 repository)을 넘기라는 것, 그리고 DB를 바꾸지 않을 것이라는 점은
추상화하지 않을 이유가 되지 않는다는 것이다. 위 판단을 유지할지 팀에서 정해야 한다.

### 상주 상태 (2026-09-26 개정)

이전 판은 "상주 상태는 dispatcher 하나뿐"이라고 적었는데, `engine`과 연결 풀이 빠져 있었다(PR #118
멘토 리뷰). 프로세스가 살아 있는 동안 메모리에 남는 객체를 두 종류로 나눠 적는다.

**바뀌는 상태.** 만드는 곳과 정리하는 곳을 반드시 적는다.

| 객체 | 위치 | 들고 있는 것 | 만드는 곳 | 정리하는 곳 |
|---|---|---|---|---|
| `engine` | `common/database.py` | DB 연결 풀 | import 시점, 모듈 전역 | 지금은 없음. #130에서 lifespan 종료 때 `engine.dispose()` |
| `dispatcher` | `realtime/dispatcher.py` | 지도별 SSE 구독자 목록, 마지막으로 처리한 `event_log.seq`, 순번 구멍 추적 시각 | import 시점에 생성, lifespan에서 초기화하고 폴링 시작 | 지금은 lifespan 종료 때 폴링 작업 취소만. #130에서 정지 대기와 SSE 정리 |

`SessionLocal`은 `engine`에 묶인 세션 공장이라 따로 상태를 들고 있지 않다.

**읽기 전용.** 기동 때 한 번 만들어지고 이후 바뀌지 않는다. `settings`(frozen dataclass), FastAPI
`app`과 모듈별 `router`가 여기 속한다. 카카오 API 호출은 `httpx.post`, `httpx.get`을 호출마다
새로 불러서 상주하는 HTTP 연결 풀은 없다.

### 접근 경로

`engine`은 `SessionLocal`을 통해서만 쓴다.

| 위치 | 하는 일 |
|---|---|
| `common/database.py::get_db_session` | 요청마다 세션 하나를 열고 `session_scope`로 커밋 또는 롤백 |
| `realtime/router.py` | SSE 재전송 조회를 짧게 열고 닫는다. 요청 단위 세션을 스트림 내내 들고 있으면 연결 풀을 계속 점유하기 때문 |
| `realtime/dispatcher.py` | 폴링과 기동 시 초기화. 요청 밖(lifespan 백그라운드 작업)에서 돈다 |

`dispatcher`의 접근 경로는 셋으로 제한된다.

| 위치 | 하는 일 |
|---|---|
| `main.py` lifespan | 기동 시 `initialize_last_seen`, 폴링 작업 시작과 종료 |
| `realtime/router.py` | SSE 연결마다 `subscribe`, 끊길 때 `unsubscribe` |
| `realtime/tests` | `_subscribers`를 직접 확인 |

**다른 모듈은 `dispatcher`를 쓰지 않는다.** 이벤트를 내보내려는 쪽은 `common.events.record_event`로
`event_log` 테이블에 쓰고, `dispatcher`는 그 테이블을 읽기만 한다(§4.1). 그래서 "이벤트를
보내려면 dispatcher를 불러야 한다"는 의존이 생기지 않는다.

### 종료 순서 (#130)

```
정지 신호 → SSE 구독 큐에 종료 표시 → 폴링 작업 종료 대기 → engine.dispose()
```

폴링은 DB 조회를 `asyncio.to_thread`로 스레드에서 돌린다. 작업을 취소해도 스레드는 멈출 수 없어서
이미 시작된 조회는 끝까지 실행된다. 그래서 폴링이 끝난 것을 확인한 뒤에 연결 풀을 닫아야 한다.

### 새 상주 상태를 만들 때

메모리에 값을 남기고 싶어지면 먼저 `event_log`처럼 **DB를 거쳐 전달할 수 있는지** 본다. 그쪽이
가능하면 그쪽을 쓴다 — 서버가 여러 대가 되어도 동작이 바뀌지 않고, 트랜잭션 경계 안에 들어가고,
테스트가 격리된다.

DB로 못 하는 경우(SSE 구독자 목록처럼 연결 자체가 프로세스에 묶인 것)에만 상주 상태를 만들고,
그때는 만드는 곳, 정리하는 곳, 접근 경로를 이 절의 표에 추가한다. 정리하는 곳이 없는 상주 상태는
만들지 않는다.

현재 `dispatcher`는 단일 서버를 전제한다. 서버가 여러 대가 되면 각 인스턴스가 따로 폴링하고
따로 구독자를 든다(멘토 리뷰에서 "우선은 단일 서버로 돌아가는 환경을 전제로 구현해보세요"로
정리된 범위다).

## 2. 장소 데이터 3층 모델

멘토 지적: "네이버·구글을 프록시로 쓰려는 방향이 틀렸다." API가 무엇을 주고 안 주는지로 설계를 시작하지 않는다. 대신 **우리가 채우고 싶은 데이터가 무엇인지**를 먼저 정하고(기획안 5-7의 실격/선호 조건 전체), 그걸 채우는 소스를 층별로 정리한다.

> **2026-10-01 결정(#53): v1은 카카오 로컬 API 응답을 어떤 형태로도 저장·캐시하지 않고 LLM에 보내지 않는다.** 저장하는 장소 데이터(이름·좌표·라벨)는 전부 **자체 DB**에서 온다 — 서울 기준, 음식점·카페는 지방행정 인허가 공공데이터, 관광지는 TourAPI. 카카오는 화면 지도(SDK)와 실시간 표시에만 쓴다. (2026-09-07의 "카카오·네이버·구글 3개 전부 실사용"과 2026-10-01 오전의 "메모리 캐시 허용"은 이 결정으로 대체됐다.)

| 층 | 값의 예 | 어디서 오나 (v1) | 저장 위치 |
|---|---|---|---|
| 1. 구조화 필드 | 이름, 좌표, 카테고리, 주소, 전화, 영업 상태 | **자체 DB 적재** — 인허가 공공데이터(음식점·카페, 폐업 제외), TourAPI(관광지). 좌표계가 위경도가 아니면 변환한다 | `places` |
| 2. 반구조화 소스 | 가격대 등 | 공공데이터 필드나 라벨 파일에서 **차원 압축**(예: 개별 가격 → `price_bucket`) | `place_facts` |
| 3. 판단(라벨) | 갑각류 포함 여부, 매운맛 전문 여부, 붐빔 정도 | **데이터 담당이 만든 라벨 파일을 적재**한다. 확인하지 않은 값은 `confidence=unknown`. **v1은 요청 중에 모델로 라벨을 만들지 않는다** | `place_facts` |

**층3은 어떤 소스를 쓰든 아무도 주지 않는다.** 이런 값 자체가 지도 API·공공데이터의 스펙 밖이다. 그래서 소스를 무엇으로 바꾸든 라벨링 파이프라인(라벨 파일 또는 v2의 모델 라벨링)은 그대로 남는다.

### 카카오 로컬 API의 역할 (v1)

운영정책과 카카오 데브톡 공식 답변(근거: 이슈 #53 최종 코멘트) 기준이다.

| 허용 | 허용되지 않음 |
|---|---|
| 실시간 호출해 화면에 잠깐 표시하고 폐기 | 응답을 어떤 형태로든 저장(가공한 라벨 포함) |
| 카카오 장소 ID·`place_url`·매칭 확인 여부와 일자 저장 | 응답 속도용 단기 캐시(메모리 포함) |
| 사용자가 직접 입력한 문자열, 기기 GPS·사진 EXIF 좌표 저장 | 응답 데이터를 LLM 등 외부로 전송 |
| 다른 출처 좌표를 카카오 지도 SDK에 올리기, 출처 표기 의무 없음 | 사용자가 카카오 지도 위에서 지정한 지점의 좌표 저장, 검색 결과를 "확정"한 좌표·SDK 장소 라벨명 저장 |
| `place_url`은 **외부 브라우저**로 열기 | `place_url`을 앱 안 WebView로 열기, 자체 DB 전체를 카카오로 일괄 조회해 매칭(대량 호출) |

이 표에서 나오는 설계 규칙:

- **검색으로 핀 찍기(#191 1번, 결정: B)**: 카카오로 검색해 결과를 화면에 보여 주고, 사용자가 하나를 고르면 서버가 **같은 자체 DB 장소**를 찾아 **자체 데이터(장소 ID·이름·좌표)만** 저장한다. 카카오 장소 ID와 `place_url`은 함께 저장해도 된다. 매칭은 사용자가 고를 때 **한 건씩만** 한다. 짝을 못 찾았을 때 무엇을 보여 줄지는 미정(#191).
- 핀·추천 후보·라벨은 모두 같은 자체 장소 ID를 쓴다. 후보와 라벨은 자체 DB에서 읽고, 카카오 원자료는 `recommend`나 `llm`으로 넘어가지 않는다(#190).
- 핀 상세의 카카오 정보는 실시간 호출로 화면에만 보여 주고 저장하지 않는다. 이미지는 카카오 로컬 API에 없다.
- **결정(#191, 2026-10-01)**: `source: search`는 짝이 되는 자체 DB 장소가 없으면 만들지 않는다(`PLACE_NOT_SUPPORTED`). 지도 길게 눌러 찍는 핀은 v1에서 뺀다(카카오 지도에서 지정한 좌표는 저장 불가 — 답변이 허용으로 오면 v2에서 "가장 가까운 자체 DB 장소로 붙이기"를 다시 본다). 자체 DB 핀은 이름을 저장하지 않는다(`places.name`).
- **실시간 핀(#382, 2026-10-07, #191 대체)**: 자체 DB에 없는 장소도 사람이 `source: live`로 핀을 남길 수 있다. 서버는 **카카오 장소 ID·사용자가 친 검색어·메모·카테고리만** 저장한다(이름·좌표는 저장하지 않는다 — 데브톡 10/1 답변: 실시간 호출 기반 사용은 허용, 장소 ID는 저장 가능). 화면이 지도를 열 때마다 카카오 JS SDK `services.Places.keywordSearch`로 검색어를 다시 찾고 장소 ID가 같은 결과의 이름·좌표로 마커를 그린다. 결과는 메모리에서만 쓰고 서버로 보내지 않는다. 가드레일 2는 "AI가 만드는 핀"에만 적용된다. 이 핀에는 `place_id`·좌표가 없어서 `recommend`(후보·기준 원)와 `shortlist`(동선 계산)는 좌표가 없는 핀을 건너뛴다.
- **숙소·기타는 v1에서 핀으로 만들 수 없다**: 자체 DB가 음식점·카페·관광지만 담는다(TourAPI 숙박은 받지 않는다). 숙소 핀을 기준점으로 쓰는 동선·반경 사유는 v1에서 동작하지 않는다.
- 개발 중 로컬 DB에 쌓인 카카오 좌표·이름은 배포 전에 지운다.

### `PlaceSource` 어댑터 (v1에서는 카카오 실시간 검색 하나)

`backend/places`의 `PlaceSource` 어댑터는 **카카오 실시간 검색(표시용)**에만 쓴다. `NaverPlaceSource`·`GooglePlaceSource`는 코드에 남아 있지만 켜지 않는다(`PLACES_SOURCES=kakao`, #188에서 기본값을 이렇게 바꾼다). 자체 DB의 적재와 검색은 어댑터가 아니라 `places` 모듈의 적재 스크립트와 DB 쿼리가 맡는다(#189).

### `places` 공개 함수 계약 (v1, #189·#190·#195가 공유)

다른 모듈은 `places.api`의 아래 함수만 부른다(`places`의 ORM·내부 모듈을 import하지 않는다). 세 이슈가 **동시에** 진행되도록 시그니처를 먼저 고정한다 — pins·recommend는 `places.testing.FakePlaces`(메모리 대역, places 세션이 **첫 PR로 먼저 올린다**)에 대고 개발·테스트하고, 실제 구현이 들어오면 대역을 갈아 끼운다.

| 함수 | 쓰는 곳 | 하는 일 |
|---|---|---|
| `match_place(hint) -> PlaceMatch \| None` | pins(핀 생성) | 힌트(`kakao_place_id`, `name`, `lat`, `lng`, `category`)에 맞는 **자체 DB 장소 한 건**을 찾는다. 읽기 전용. 반경 상한(기본 300m)·후보 수 상한·분류 일치·이름 일치를 모두 만족할 때만 돌려준다. 동명 점포가 여럿이면 이름 일치 + 거리 순으로 한 건, **확신이 낮으면 `None`**(엉뚱한 곳에 핀이 꽂히는 것보다 거절이 낫다) |
| `record_kakao_match(place_id, kakao_place_id, kakao_place_url) -> None` | pins(핀 생성 같은 트랜잭션) | 매칭된 장소에 카카오 장소 ID·URL·확인 일자만 기록한다(`places.kakao_*`). **첫 값 유지**(#248) — 이미 다른 ID가 있으면 덮어쓰지 않고, 같은 ID면 확인 일자만 갱신한다. pins는 `kakao:<숫자 1~20자리>`일 때만 부른다(형식이 틀리면 매칭은 하되 기록하지 않는다) |
| `pinnable_flags(hints) -> list[bool]` | 검색 응답(`GET /places/search`) | 힌트마다 `match_place`가 성공할지 읽기만 해서 계산한다. **카카오 ID를 기록하지 않는다**(`record_kakao_match`와 분리) |
| `get_places(place_ids) -> dict[str, PlaceInfo]` | pins(핀 응답), recommend(후보 응답) | `name`, `lat`, `lng`, `category`, `kakao_place_url`을 배치로 조회(N+1 금지). 없는 ID는 키에서 빠진다 |
| `search_nearby_own(category, areas) -> list[PlaceRef]` | recommend(후보 풀) | 반경 안의 **영업 중**(`status='open'`) 장소의 `place_id`·좌표. 카테고리는 음식점·카페·관광지 |
| `get_facts(place_ids) -> dict[str, list[FactLabel]]` | recommend(라벨) | `place_facts`의 `fact_key`·`value`·`confidence`를 그대로(없으면 빈 리스트). 호출하는 쪽이 `unknown_policy`를 적용한다 |

- **`db` 선택 키워드 인자(#199에서 추가, 6개 함수 전부 `*, db: Session | None = None`)**: `db=db`를 넘기면 그 요청 트랜잭션에 참여한다(커밋은 호출한 쪽이 한다). **pins는 `record_kakao_match`를 반드시 `db=db`로 부른다** — 핀 생성과 같은 트랜잭션이어야 한다. 안 넘기면 places가 짧은 세션을 직접 열어 쓰고 닫는다(읽기 전용 호출은 충분하지만 호출마다 연결을 쓴다). `FakePlaces`도 같은 인자를 받는다.
- `place_id`는 문자열(`places.id`의 UUID). 타입은 `places/schemas.py`의 불변 dataclass: `PlaceHint`, `PlaceMatch`, `PlaceInfo`, `PlaceRef`, `FactLabel`.
- **카카오 원자료는 이 함수들의 입출력 어디에도 없다.** `kakao_place_id`·`kakao_place_url`만 예외(저장 허용 범위).
- 기존 `places.api`의 실시간 카카오 검색(`search_by_name`, 표시용)과 `get_raw_facts`(항상 빈 값)는 그대로 둔다. `search_nearby`(카카오 실시간 후보 풀)와 `resolve_place`는 recommend·pins가 위 함수로 옮겨 가면 지운다(#190, #195).

### 층2 차원 압축 설계

`place_facts`에는 **원본 가격 숫자를 저장하지 않는다.** `price_bucket ENUM(low|mid|high)`처럼 압축된 값만 저장한다 — 필요한 판정값만 남기고 원본은 버리는 데이터 최소화 설계다. 압축 로직(임계값)은 `docs/constraints.md`에서 관리한다.

> **✅ 2026-10-01 — 지도 API 이용약관 문제(#53)는 위 결정으로 정리됐다.** 카카오 응답은 저장하지 않으므로 `place_facts`의 라벨은 카카오 응답을 가공한 값이 아니라 자체 DB 장소에 붙은 값이다. 공공데이터 데이터셋별 이용허락 범위와 갱신 주기는 #189에서 확인한다.

## 3. 프리시딩(사전 라벨링) — 온디맨드의 대기시간 문제 해소

> **2026-10-01 — v1 적용 범위(#53):** v1에서는 **요청 중에 모델로 라벨을 만들지 않고**(검색 기반 보강, 웹 검색 포함), 라벨은 자체 DB `place_facts`에서 읽는다. 라벨은 데이터 담당의 라벨 파일을 적재해 채우고, 비어 있으면 `confidence=unknown`으로 두어 `unknown_policy`를 그대로 적용한다. 아래의 프리시딩 큐·온디맨드 폴백·검색 기반 보강은 **v2(모델 라벨링)** 설계로 남겨 둔다.

기획안 5-8은 라벨링을 요청 경로 한가운데 뒀다("반경 검색으로 후보 확보 → 캐시 미스 시 그 자리에서 라벨링"). 캐시가 비어 있는 첫 실행에서는 **후보 전체(예: 18곳)에 대해 LLM 라벨링이 순차 또는 병렬로 돌고, 그 지연이 그대로 사용자 대기시간이 된다.** 멘토: "온디맨드가 제일 좋지만 인퍼런스 타임이 일반 서비스 기준으로는 꽤 느리다."

### 해결 — 프리시딩 + 온디맨드 폴백 (둘 다 필요, 대체 관계 아님)

데이터 출처(위 3층 모델)는 온디맨드든 프리시딩이든 동일하다. 다른 것은 **언제 만드느냐**뿐이다.

```
[배치] 데모/발표 대상 지역 1~2곳 선점 라벨링           ← v1, 수동 큐잉
        ↓
[트리거] 지도 생성 시 그 지역 프리시딩 잡 큐잉 — 지역 = 생성 시 받은 region(#22),
        없으면 첫 핀 좌표로 확정
        ↓
   [사용자가 핀 찍고 반응 남기는 시간 — 통상 수 분~수 시간]
   5-4: 카테고리별 의견 남긴 핀이 ceil(N/2) 이상이어야 추천 버튼 활성화
        ↓
   [트리거 2, #99] 핀이 생기거나 처음 ♥를 받을 때 그 장소도 큐잉
   ③-b가 ♥ 장소의 라벨을 선호 신호로 쓴다 — 요청 경로에서 라벨링하지 않으려고
   이 시간대에 미리 채운다 (docs/constraints.md "선호 점수 계산" 참고)
        ↓
「추천 받기」 실행 시점                                  ← 대부분 이미 채워져 있음
        ↓                              ↓
   라벨 있음 → 그대로 사용        라벨 없음 → 온디맨드 폴백 (기존 5-8 경로)
                                        ↓
                              그래도 못 채우면 confidence=unknown
                                        ↓
                          docs/constraints.md의 unknown_policy로 분기
                          (이번 요청은 여기서 끝 — 사용자는 기다리지 않는다)
                                        ↓
                     [비동기, 사용자 대기 없음] 검색 기반 보강 작업을 큐에 넣는다
                                        ↓
                          다음에 같은 후보가 다시 뜨면 이미 채워져 있음
```

5-4의 수동 트리거 + 임계값이 만드는 자연 지연이 프리시딩 윈도우를 공짜로 만들어준다. 챗봇형 서비스라면 이 여유가 없다(3절, 챗봇과의 차이).

### 검색 기반 보강 (2026-09-07 결정)

온디맨드 폴백까지 거쳤는데도 unknown인 경우, **이번 요청을 그 자리에서 더 기다리게 하지 않는다** — 지금 요청은 `unknown_policy`대로 즉시 처리하고 응답한다. 대신 `seeding`이 "이 (장소, fact_key)는 정보가 부족했다"를 별도 큐에 넣어 **비동기로** 보강을 시도한다.

보강 작업에서는 `llm`의 ③-a-1 호출에 검색 도구를 붙인다 — 모델이 라벨을 못 정하면 도구를 불러 추가 정보를 찾아본 뒤 다시 판단한다. 도구는 두 단계로 좁힌다.

1. **우리 소스 재조회 우선** — 이미 확보한 `place_url`로 `PlaceSource.detail()`을 다시 불러 메뉴·리뷰 원문을 더 얻는다.
2. **오픈 웹 검색은 최후 수단** — 1번으로도 안 되면 웹 검색을 허용하되, 안전 조건(`contains_shellfish`·`spicy_focused`·`oily_focused`)에는 신뢰 가능한 도메인(지도 서비스·가게 공식 사이트)으로 제한한다. 결과가 지저분할수록 안전 조건에 쓰기 위험하기 때문이다.

**모델이 판단(라벨)만 만든다는 원칙은 그대로다(가드레일 7)** — 도구로 자율성이 커지는 건 "정보를 더 찾을지" 뿐이고, "이 가게를 후보에서 뺄지"는 여전히 코드(③-a-2)가 정한다. 그리고 검색으로 찾은 근거에도 기존 규칙(원자료에 실제로 있는 근거만 인용, 없으면 지어내지 않고 unknown 유지)이 그대로 적용된다 — 검색 결과라고 근거 검증을 느슨하게 하지 않는다.

라벨 캐시는 장소 단위 전역이다(5-8) — 같은 가게가 다른 팀의 다른 지도에서 후보로 잡혀도 재사용한다. 지도가 쌓일수록, 특히 프리시딩 대상 지역 안에서는 재라벨링 비율이 줄어든다.

## 4. 실시간 동기화 — SSE 확정

멘토: "핀 찍는 이벤트 순간에만 전파하면 되고 그 외에는 상태가 유지된다. 클라이언트→서버 빈도가 매우 적어서 웹소켓보다 더 간단한 방식으로 충분할 수 있다." 클라이언트→서버는 일반 HTTP POST/PATCH, 서버→클라이언트는 SSE로 확정한다(#13을 결정에서 구현으로 전환).

채널은 2개로 분리한다 — 전체 채널(지도 단위, 게시된 상태 변화)과 개인 채널(요청자 본인의 비공개 AI 후보·run 진행 상태). 5-5-1의 "요청한 사람에게만 보인다"를 채널 분리로 구조적으로 강제한다. 상세 이벤트 스키마는 `docs/events.md`.

## 6. CI/배포 방향 (멘토 피드백 6)

"6명은 적은 인원이 아니다. PR에서 테스트되는 것 + 병합 시 문제없는지 확인 — 참조 없이 어긋나는 부분이 빌드 깨짐으로 잡힌다. 배포 데모가 커밋마다 올라가면 백엔드가 프론트 환경을 구성하지 않고도 확인할 수 있다."

- PR 파이프라인: 단위 테스트 + `docs/api-spec.yaml` 검증(lint) + 계약 테스트(구현이 스펙과 일치하는지)
- main 병합 시: Cloud Run으로 배포 (컨테이너만 올리면 되므로 인프라 관리 부담이 적다 — 멘토도 "편한 걸 쓰면 된다"고 확인)
- 프리뷰: PR마다 임시 환경 또는 최소한 목 서버(`docs/openapi-workflow.md`)로 프론트가 항상 최신 계약을 볼 수 있게 한다
