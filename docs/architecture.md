# 기술 아키텍처

작성 기준: `최종기획안.md` + 기술 멘토링 피드백(2026-09-02)
정본 관계: 이 문서가 모듈 경계·데이터 흐름의 정본이다. API 계약 자체는 `api-spec.yaml`을 본다.

멘토 피드백 핵심 2가지가 이 문서의 축이다.
1. "어떤 API를 쓸지"가 아니라 **우리 서버·DB를 두고 거기서 한 번 추상화**한다 — API 선택에 제약을 두지 않는다.
2. 장소 서비스는 **데이터가 전부**다. 라벨링(=우리가 만든 1차 데이터)이 곧 해자다.

## 1. 모듈 경계

각 모듈이 서브 디렉토리 Claude Code 1개의 작업 범위(`backend/<module>/`)가 된다. 모듈은 자신의 DB 테이블만 직접 쓰고, 다른 모듈의 데이터는 반드시 그 모듈이 정의한 API/함수 계약을 통해서만 읽는다.

| 모듈 | 책임 | 기획안 근거 | 의존 |
|---|---|---|---|
| `auth` | 카카오 OAuth 콜백, httpOnly 쿠키 발급, 로그인/로그아웃/탈퇴, 탈퇴 시 데이터 삭제 범위 | 13절, 12절 | — |
| `authz` | 롤 → 접근범위 + 액션 선언적 권한 판정, 모든 응답에 `permissions` 주입 | 15-1 (재설계) | `maps` |
| `maps` | 지도 생성, 초대 링크, 구성원 관리·색 배정, 구성원 수(N) 관리 | 6절 | `auth` |
| `pins` | 핀 CRUD, 반응(♥/△/🚫/?), 중복 판정, 분류×종류 이중 필터 집계 | 5-1, 5-2, 4절 | `maps`, `places` |
| `places` | `PlaceSource` 어댑터, `place_facts` 자체 장소 DB, 수집·차원압축 파이프라인 | #14, 멘토 피드백 5 | — (외부 API만) |
| `seeding` | 프리시딩 배치 워커, 지도 생성 시 지역 큐잉 | 신규(D3) | `places`, `maps` |
| `recommend` | 추천 오케스트레이션(①②③-a-2④), 근거 조립, 검색범위(circles) 계산, funnel, 제외목록, 재시도 | 3절, 5-5~5-6-1 | `pins`, `places`, `llm` |
| `llm` | 모델 호출 3곳 + 프롬프트 + 구조화 출력 스키마 | 8절 | (외부 LLM API) |
| `shortlist` | 확정 리스트 추가/제외, 동선 계산(모델 미사용) | 5-3, 5-10 | `pins`, `maps` |
| `realtime` | SSE 채널(전체/개인), `event_log` 폴링·재동기화 | 5-5-1 | `common` |
| `common` | 에러 포맷, 멱등키, 페이지네이션, `seq` 채번, 좌표 유틸(PostGIS), `event_log` 발행 계약(`record_event`) | #2 | — |

의존 방향은 위에서 아래로만 흐르게 한다. `pins`가 `recommend`를 참조하지 않는다(추천이 핀을 만들지만 핀이 추천을 알 필요는 없다).
예외였던 `realtime`의 역방향 의존(전 모듈→realtime)은 이벤트 계약을 `common`으로 내려서
없앴다 — 이제 화살표는 전부 아래로만 흐른다. 각 모듈은 `common.events.record_event(db, event)`
로 쓰고, `realtime`은 `event_log`를 읽기만 한다.

## 1.1 기능 실행 함수(flow) — 언제, 어디에 두는가

한 요청이 **두 모듈 이상의 테이블**을 같은 커밋 안에서 바꾸면 그 모듈이 `flows.py`에 기능
실행 함수를 만든다. 한 모듈의 테이블만 바꾸면 기존 `service.py`가 그대로 처리한다.

기능 실행 함수는 **`docs/api-spec.yaml`에서 그 엔드포인트의 태그가 가리키는 모듈**에 둔다 —
별도의 `usecases/` 공유 디렉토리를 만들지 않는다. 6개 세션이 각자 디렉토리에서 병렬로 작업하는
이 팀의 구조상, 아무도 소유하지 않는 공유 디렉토리는 모든 교차 기능의 병목이 된다.

지금 flow가 필요한 것은 둘뿐이다:

| flow | 엔드포인트 | 위치 |
|---|---|---|
| 후보 게시 | `POST /candidates/{candidateId}/publish` | `backend/recommend/flows.py::publish_candidate` |
| 핀 확정 | `POST /maps/{mapId}/shortlist` | `backend/shortlist/flows.py::confirm_pin` |

**flow 함수 자체는 순서와 실패 처리만 담당한다 — 판단 로직은 두지 않는다.** 판단은 각 모듈의
`core.py` 순수 함수에 있다(`docs/code-quality.md`). flow에 `if`가 늘어나기 시작하면 그 분기는
core.py로 옮긴다.

**flow가 필요 없는 것들** (기존 `service.py`가 그대로 처리):

| 작업 | 바뀌는 테이블 |
|---|---|
| 핀 CRUD, 반응 등록/삭제 | `pins` + `event_log` |
| 확정 리스트 순서 변경 | `shortlist_items`만 |
| 동선 계산 | 계산 결과 + `event_log` |
| 근거 추가/토글, 추천 실행 생성 | `recommend` 테이블 + `event_log` |
| 초대 수락 | `memberships` + `event_log` |

`event_log`는 "다른 모듈의 테이블"로 세지 않는다 — 모든 모듈이 `common.events.record_event`로
쓰도록 설계됐기 때문이다(§4.1). 그렇지 않으면 사실상 모든 쓰기가 flow가 되어 이 구분 자체가
무의미해진다.

교차 모듈 쓰기는 **`<module>/api.py`**를 통해서만 한다 — 다른 모듈의 `service.py`나 `models.py`를
직접 import하지 않는다. 예: `recommend/flows.py`가 `pins.api.create_ai_pin(...)`을 부른다.

## 1.2 엔드투엔드 흐름 예시 — 후보 게시

지금까지 이 문서에 모듈을 가로지르는 실행 흐름이 없었다(멘토 리뷰 지적). 가장 복잡한 흐름
하나를 예로 남긴다 — 나머지 흐름은 `docs/api-spec.yaml`과 각 모듈 `flows.py`/`service.py`를
따라가면 같은 패턴이다.

```
클라이언트 ─POST /candidates/{id}/publish→ recommend/router.py (HTTP 셸)
   → recommend/flows.py::publish_candidate           ← 순서·트랜잭션 담당, 판단 없음
       1. recommend/service.py  후보·run 조회                              (404)
       2. recommend/core.py::check_publishable(...)  순수 판정             (409/403)
       3. pins.api.create_ai_pin(db, ...)             INSERT pins          (커밋 안 함)
       4. recommend/service.py  UPDATE candidates.published_pin_id        (커밋 안 함)
       5. common.events.record_event(db, pin_published_event(pin))        (커밋 안 함)
   ← 반환
   common/database.py::get_db  ── COMMIT (요청당 이 한 곳뿐) ──→ pins·candidates·event_log 동시 확정
   realtime/dispatcher.py  event_log 폴링 → 전체 채널 SSE
```

실패하면 1~5 전부 롤백된다 — pins 행만 생기고 이벤트는 안 나가는 상태는 구조적으로 불가능하다
(§4.1).

## 2. 장소 데이터 3층 모델

멘토 지적: "네이버·구글을 프록시로 쓰려는 방향이 틀렸다." API가 무엇을 주고 안 주는지로 설계를 시작하지 않는다. 대신 **우리가 채우고 싶은 데이터가 무엇인지**를 먼저 정하고(기획안 5-7의 실격/선호 조건 전체), 그걸 채우는 소스를 층별로 정리한다.

| 층 | 값의 예 | 어디서 오나 | 저장 위치 |
|---|---|---|---|
| 1. 구조화 필드 | 좌표, 카테고리, 주소, 전화, `place_url` | `PlaceSource` 어댑터 (Kakao/Google/Naver 중 무엇이든) | `places` |
| 2. 반구조화 소스 | 메뉴 가격, 영업시간, 리뷰 텍스트 | 어댑터가 준 `place_url` 등을 파싱 → **차원 압축**(예: 개별 가격 평균 → `price_bucket`) | `place_facts` |
| 3. 모델 판단 | 갑각류 포함 여부, 매운맛 전문 여부, 붐빔 정도 | LLM이 층1·2를 읽고 판단 | `place_facts` |

**층3은 어떤 API를 쓰든 아무도 주지 않는다.** "카카오라서 없다"가 아니라 이런 값 자체가 지도 API의 스펙 밖이다. 그래서 API를 무엇으로 바꾸든 라벨링 파이프라인은 그대로 남는다 — 이게 어댑터 설계가 실제로 절약해주는 부분이다.

### `PlaceSource` 어댑터 계약 (개념)

```
interface PlaceSource {
  search(keyword, geo_bounds) -> RawPlace[]   // 층1
  detail(source_id) -> RawPlaceDetail          // 층1 + 층2 원문(가능한 만큼)
}
```

구현체: `KakaoPlaceSource`·`NaverPlaceSource`·`GooglePlaceSource` — **2026-09-07 결정으로 v1부터 3개 전부 실사용**(비용순 폴백: 카카오→네이버→구글, `backend/places/CLAUDE.md` 참고). 소스 선택은 카테고리·지역별로 설정 가능해야 한다 — 하나로 고정하지 않는다.

### 층2 차원 압축 설계

`place_facts`에는 **원본 가격 숫자를 저장하지 않는다.** `price_bucket ENUM(low|mid|high)`처럼 압축된 값만 저장한다 — 필요한 판정값만 남기고 원본은 버리는 데이터 최소화 설계다. 압축 로직(임계값)은 `docs/constraints.md`에서 관리한다.

> **🚨 2026-09-07 — 이 설계가 각 지도 API의 이용약관상 허용되는지 자체가 현재 미확정이다.** 카카오 개발자 포럼에서 로컬 API 결과의 영구 저장을 아예 금지하는 취지의 답변이 다수 확인됐다(ID·URL만 저장 가능, 좌표조차 불가할 수 있음). **파생 라벨(`place_facts`)도 저장 금지 대상인지까지 확인 대상이다.** 진행 상황·확인 순서는 이슈 [#53](https://github.com/kakaotechcampus-4/ktc4-chungnam-2/issues/53) 참고 — **이 이슈가 풀리기 전엔 `backend/places`의 실제 수집·저장 파이프라인을 구현하지 않는다.** 최악의 경우(좌표·라벨 모두 영구 저장 불가) 대비책: 반경 검색을 실시간 API 호출로 전환하고 필요시마다 재라벨링하는 방향으로 이 절 자체를 다시 쓴다.

## 3. 프리시딩(사전 라벨링) — 온디맨드의 대기시간 문제 해소

기획안 5-8은 라벨링을 요청 경로 한가운데 뒀다("반경 검색으로 후보 확보 → 캐시 미스 시 그 자리에서 라벨링"). 캐시가 비어 있는 첫 실행에서는 **후보 전체(예: 18곳)에 대해 LLM 라벨링이 순차 또는 병렬로 돌고, 그 지연이 그대로 사용자 대기시간이 된다.** 멘토: "온디맨드가 제일 좋지만 인퍼런스 타임이 일반 서비스 기준으로는 꽤 느리다."

### 해결 — 프리시딩 + 온디맨드 폴백 (둘 다 필요, 대체 관계 아님)

데이터 출처(위 3층 모델)는 온디맨드든 프리시딩이든 동일하다. 다른 것은 **언제 만드느냐**뿐이다.

```
[배치] 데모/발표 대상 지역 1~2곳 선점 라벨링           ← v1, 수동 큐잉
        ↓
[트리거] 지도 생성 시 (첫 핀 좌표로 지역 확정) 그 지역 프리시딩 잡 큐잉
        ↓
   [사용자가 핀 찍고 반응 남기는 시간 — 통상 수 분~수 시간]
   5-4: 카테고리별 의견 남긴 핀이 ceil(N/2) 이상이어야 추천 버튼 활성화
        ↓
「추천 받기」 실행 시점                                  ← 대부분 이미 채워져 있음
        ↓                              ↓
   라벨 있음 → 그대로 사용        라벨 없음 → 온디맨드 폴백 (기존 5-8 경로)
                                        ↓
                              그래도 못 채우면 confidence=unknown
                                        ↓
                          docs/constraints.md의 unknown_policy로 분기
                          (이번 요청은 여기서 끝 — 사용자는 기다리지 않는다)
                                        ↓
                     [비동기, 사용자 대기 없음] 검색 기반 보강 작업을 큐에 넣는다
                                        ↓
                          다음에 같은 후보가 다시 뜨면 이미 채워져 있음
```

5-4의 수동 트리거 + 임계값이 만드는 자연 지연이 프리시딩 윈도우를 공짜로 만들어준다. 챗봇형 서비스라면 이 여유가 없다(3절, 챗봇과의 차이).

### 검색 기반 보강 (2026-09-07 결정)

온디맨드 폴백까지 거쳤는데도 unknown인 경우, **이번 요청을 그 자리에서 더 기다리게 하지 않는다** — 지금 요청은 `unknown_policy`대로 즉시 처리하고 응답한다. 대신 `seeding`이 "이 (장소, fact_key)는 정보가 부족했다"를 별도 큐에 넣어 **비동기로** 보강을 시도한다.

보강 작업에서는 `llm`의 ③-a-1 호출에 검색 도구를 붙인다 — 모델이 라벨을 못 정하면 도구를 불러 추가 정보를 찾아본 뒤 다시 판단한다. 도구는 두 단계로 좁힌다.

1. **우리 소스 재조회 우선** — 이미 확보한 `place_url`로 `PlaceSource.detail()`을 다시 불러 메뉴·리뷰 원문을 더 얻는다.
2. **오픈 웹 검색은 최후 수단** — 1번으로도 안 되면 웹 검색을 허용하되, 안전 조건(`contains_shellfish`·`spicy_focused`·`oily_focused`)에는 신뢰 가능한 도메인(지도 서비스·가게 공식 사이트)으로 제한한다. 결과가 지저분할수록 안전 조건에 쓰기 위험하기 때문이다.

**모델이 판단(라벨)만 만든다는 원칙은 그대로다(가드레일 7)** — 도구로 자율성이 커지는 건 "정보를 더 찾을지" 뿐이고, "이 가게를 후보에서 뺄지"는 여전히 코드(③-a-2)가 정한다. 그리고 검색으로 찾은 근거에도 기존 규칙(원자료에 실제로 있는 근거만 인용, 없으면 지어내지 않고 unknown 유지)이 그대로 적용된다 — 검색 결과라고 근거 검증을 느슨하게 하지 않는다.

라벨 캐시는 장소 단위 전역이다(5-8) — 같은 가게가 다른 팀의 다른 지도에서 후보로 잡혀도 재사용한다. 지도가 쌓일수록, 특히 프리시딩 대상 지역 안에서는 재라벨링 비율이 줄어든다.

## 4. 실시간 동기화 — SSE 확정

멘토: "핀 찍는 이벤트 순간에만 전파하면 되고 그 외에는 상태가 유지된다. 클라이언트→서버 빈도가 매우 적어서 웹소켓보다 더 간단한 방식으로 충분할 수 있다." 클라이언트→서버는 일반 HTTP POST/PATCH, 서버→클라이언트는 SSE로 확정한다(#13을 결정에서 구현으로 전환).

채널은 2개로 분리한다 — 전체 채널(지도 단위, 게시된 상태 변화)과 개인 채널(요청자 본인의 비공개 AI 후보·run 진행 상태). 5-5-1의 "요청한 사람에게만 보인다"를 채널 분리로 구조적으로 강제한다. 상세 이벤트 스키마는 `docs/events.md`.

## 5. 권한 — 선언적 모델

멘토: "롤로 조건 판단을 하지 말고, 롤 → 접근 가능 범위 + 가능한 액션으로 권한이 내려오게 설계하라. 나중에 역할 추가가 쉽다." 상세는 `docs/permissions.md`.

## 6. CI/배포 방향 (멘토 피드백 6)

"6명은 적은 인원이 아니다. PR에서 테스트되는 것 + 병합 시 문제없는지 확인 — 참조 없이 어긋나는 부분이 빌드 깨짐으로 잡힌다. 배포 데모가 커밋마다 올라가면 백엔드가 프론트 환경을 구성하지 않고도 확인할 수 있다."

- PR 파이프라인: 단위 테스트 + `docs/api-spec.yaml` 검증(lint) + 계약 테스트(구현이 스펙과 일치하는지)
- main 병합 시: Cloud Run으로 배포 (컨테이너만 올리면 되므로 인프라 관리 부담이 적다 — 멘토도 "편한 걸 쓰면 된다"고 확인)
- 프리뷰: PR마다 임시 환경 또는 최소한 목 서버(`docs/openapi-workflow.md`)로 프론트가 항상 최신 계약을 볼 수 있게 한다
