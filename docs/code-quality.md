# 코드 품질 — 클린 코드 원칙 + AI 시대 리뷰 기준

## 클린 코드 원칙 — 기능형 코어 / 명령형 셸

출처: [The Grand Unified Theory of Software Architecture](https://danuker.go.ro/the-grand-unified-theory-of-software-architecture.html)

핵심 하나로 요약된다: **의존성 화살표는 항상 안쪽(비즈니스 로직)을 향해야 하고, I/O는 바깥쪽 얇은 층에만 몰아둔다.**

- **코어는 순수 함수로 짠다** — 입력을 받아 값을 반환할 뿐, DB·네트워크·시간·전역상태를 건드리지 않는다. 모의 객체(mock) 없이 직접 호출해서 테스트할 수 있어야 정상이다.
- **셸은 얇게, I/O만** — 입력 수집 → 코어 호출 → 출력 변환/전송. 셸에는 분기·계산 로직을 두지 않는다. 셸의 검증은 통합 테스트로만 한다.
- **바깥은 안쪽을 모른다** — DB나 외부 API가 우리 비즈니스 로직을 호출하는 형태를 만들지 않는다. 항상 코어 → (필요시) 어댑터 방향이다.
- **이름이 계층을 드러내야 한다** — `call_json_api`처럼 구현 디테일을 노출하는 이름 대신, 코어 함수는 하는 일을, 셸 함수는 오케스트레이션임을 이름으로 보여준다.
- **결합을 줄이는 게 전부다** — 이 원칙들의 목적은 전부 "변경이 한 곳에서 끝나게" 하는 것이다.

**이 프로젝트에서의 매핑** — `docs/constraints.md`의 필터 판정, 5-6-1 원 겹침 계산, 5-10 최근접 이웃 동선 계산은 전부 순수 함수로 짤 수 있는 코어다(입력=핀·조건, 출력=통과여부·순서). `backend/recommend`·`backend/shortlist`의 API 핸들러는 셸이다 — DB 읽고, 코어 함수 호출하고, 응답으로 변환만 한다. `backend/llm`은 예외적으로 셸에 가깝다(외부 API 호출이 본질) — 대신 입력 구조화·출력 파싱은 순수 함수로 분리할 수 있다.

## AI가 코드를 쓰는 시대의 리뷰 기준

기존엔 스타일·문법을 사람이 훑어야 했지만, AI가 그 수준은 이미 잘한다. **사람이 봐야 할 곳이 바뀌었다** — 아래는 업계에서 실제로 옮겨가고 있는 리뷰 초점이다.

| 볼 것 | 왜 |
|---|---|
| **경계·스코프** — PR이 요청받은 것만 건드렸는가 | AI는 "하는 김에" 범위를 넓히는 경향이 있다. 이 프로젝트에선 특히 `backend/<module>/CLAUDE.md`의 "넘지 말 것"을 실제로 지켰는지 |
| **계약 준수** — API 응답이 `docs/api-spec.yaml`과 일치하는가 | 스타일보다 훨씬 더 자주, 더 조용히 깨진다 |
| **도메인 규칙 준수** — `docs/constraints.md`의 `unknown_policy`, 가드레일 10개 | 일반적인 코드 리뷰 체크리스트엔 없는, 이 프로젝트 고유의 위험 지점 |
| **테스트의 주장(assertion) 내용** — 테스트가 존재/통과가 아니라 실제로 실패 케이스를 잡는가 | AI가 쓴 테스트는 "통과하도록" 쓰이기 쉽다. mock이 자기 자신을 검증하고 있지 않은지 확인 |
| **실패를 감추는 코드** — 조용한 fallback, 무의미한 기본값 | 에러가 사라지면 나중에 훨씬 비싸게 돌아온다 |
| **PR 설명의 "왜"** | AI 코드는 "무엇"은 자명하지만 "왜 이렇게"가 비어있기 쉽다. 이게 없으면 리뷰어가 의도를 추측해야 한다 |

**리뷰 전략**: 줄 단위로 다 읽지 않는다. 위 6가지에 집중하고, 위험도가 높은 파일(인증·권한·데이터 삭제·결제성 로직 없음이지만 이 프로젝트에선 실격 필터·권한 판정)은 더 자세히, 반복적인 CRUD 보일러플레이트는 가볍게 훑는다.
