# 제약 레지스트리

작성 기준: 최종기획안 5-7절 + 이번 세션 결정(D4)
**이 문서의 값은 루트만 바꾼다.** 서브 모듈(`llm`, `recommend`, `places`)이 여기 없는 조건을 새로 만들거나 `unknown_policy`를 임의로 바꾸면 안 된다 — 최우선 성공지표(실격 조건 위반율 0%, 기획안 10절)가 이 값들에 직접 걸려 있다.

## 왜 `unknown_policy`가 조건마다 다른가

기획안 2절이 실격/선호를 나눈 논리를 그대로 확장한다. 판정을 못 했을 때("모름", 가드레일 8) 틀렸을 때의 비용이 조건마다 다르다.

- **안전 조건**(재료·알러지·매운맛): 틀리면 "못 먹는 걸 추천하는 사고"(기획안 50줄, 재첩국·초밥 사례). 모르면 **제거**한다 — 후보가 줄어드는 게 사람이 다치는 것보다 싸다.
- **취향 조건**(가격·붐빔·수용인원·영업여부): 틀려도 "취향이 안 맞는 정도"(기획안 2절 표). 모른다고 제거하면 미준비 지역(architecture.md 3절 프리시딩 전)에서 결과가 자주 0개가 된다. **통과시키되 「확인 필요」 배지**를 붙여 사람이 최종 판단하게 한다(가드레일 8 "확정하지 않는다"를 배지로 구현).

## 조건별 정의

| `fact_key` | 카테고리 | 종류 | 원문(5-7) | `unknown_policy` | 근거 |
|---|---|---|---|---|---|
| `contains_shellfish` 등 재료 태그 | 전체 | hard | 갑각류 제외 등 | **exclude** | 기획안 50줄 알러지 사고 사례 |
| `spicy_focused` | 음식점 | hard | 매운맛 전문 제외 | **exclude** | 실측 실패 6건 중 다수가 "매워요" |
| `oily_focused` | 음식점 | hard | 기름진 메뉴 제외 | **exclude** | 위와 동일 성격(안전·건강) |
| `price_bucket` (per-category 상한 비교) | 전체 | hard | 1인/음료/1박/입장료 상한 | pass + `needs_check` | 취향 영역(D4) |
| `capacity_min` | 숙소 | hard | 3인 이상 수용 | pass + `needs_check` | 취향 영역 |
| `is_crowded_large` | 카페/관광지 | hard | 붐비는 대형 카페·명소 제외 | pass + `needs_check` | 취향 영역 |
| `is_open` | 전체 | hard(코드 판정, 5-6 순서 3) | 영업 종료 제거 | pass + `needs_check` | 취향 영역. 라벨링이 아니라 실시간 조회 실패 시 적용 |
| `within_radius` | 전체 | hard(코드 판정, 5-6-1) | 도보 15분 등 | 해당 없음 | 좌표는 항상 known — `places.geom`이 없으면애초 후보에 못 들어옴 |
| `wait_short` | 음식점 | soft | 대기 짧은 곳 | pass (순위에서 중립 처리) | 선호는 애초에 걸러내지 않음(5-1) |
| `quiet` `comfortable_seat` `local_flavor` 등 | 카페/숙소/관광지 | soft | 조용함·좌석·지역색 등 | pass (순위에서 중립 처리) | 선호는 순위에만 영향, 후보를 거르지 않음 |

가격 버킷 임계값(저/중/고 경계, 5-7절 카테고리별 상한과의 매핑)은 `places` 모듈 구현 시 `docs/api-spec.yaml`의 `PriceBucket` 스키마와 함께 확정한다.

## 실격 필터 순서에서의 적용 지점

기획안 5-6절 순서 4단계("활성 실격 조건별 제거")에서 이 표를 그대로 순회한다. `−`로 뺀 근거(evidence_lines.is_active=false)는 fact_key 매핑이 있어도 적용하지 않는다.
