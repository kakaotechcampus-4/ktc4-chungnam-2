# PR 전달용 요약 코멘트

인자로 PR 번호나 URL을 받는다. 없으면 현재 브랜치의 PR(`gh pr view --json number`)을 쓴다.

## 순서

1. PR을 읽는다: `gh pr view <번호> --json title,body,files,baseRefName` + `gh pr diff <번호>`.
   본문만 믿지 말고 diff로 실제 바뀐 걸 확인한다.
2. 이미 같은 목적의 요약 코멘트가 있는지 본다(`gh pr view <번호> --comments`). 있으면 새로 달지 말고 사용자에게 물어본다.
3. 쓰는 사람과 받는 사람을 정한다.
   - 쓰는 사람은 사용자다. 사용자의 역할(FE·`backend/<module>` 담당·AI·PM 등)을 먼저 확인한다. 대화나 메모리에 없으면 물어본다. 짐작하지 않는다.
   - 받는 사람은 이 PR 때문에 실제로 뭔가 해야 하는 사람이다. 예: 스펙이 바뀌었는데 백엔드가 아직이면 그 모듈 담당.
   - 사용자 본인 몫의 작업은 남에게 부탁하는 문장으로 쓰지 않는다("제가 만들 예정입니다"처럼 쓴다).
4. 아래 형식으로 쓰고 `gh pr comment <번호> --body-file -`로 단다.
5. 코멘트 URL을 사용자에게 알려준다.

## 내용

받는 사람이 **자기 작업에 필요한 것만** 넣는다. PR 본문을 다시 옮기지 않는다.

- 첫 줄: 무엇이 바뀌었는지 한 문장
- `**1) 제목 (근거 절·이슈)**` 식으로 번호 붙인 짧은 묶음. 각 묶음 아래는 `-` 항목 2~5개
- API 변경이면: 엔드포인트, 요청·응답 모양과 예시, 필수인지 선택인지
- 받는 사람이 할 일(예: `contracts`에서 `npm run gen:types`), 목 서버를 바로 쓸 수 있는지, 실제 백엔드가 됐는지
- 마지막에 **아직 정해지지 않은 것**
- 코드 변경이 없으면 끝에 한 줄로 밝힌다

## 말투

- "~습니다/~입니다"로 쓴다. 예: "필수는 아닙니다!", "실제 백엔드는 아직입니다.", "~해주시면 될 거 같습니다."
- "~에요/~해요"는 쓰지 않는다.
- "계약"이라는 말은 쓰지 않는다. "API 바뀐 부분", "스펙"처럼 풀어 쓴다.
- AI가 쓴 티가 나는 표현(과한 꾸밈, 이모지 남발, "~를 통해", "~에 대해")은 빼고, 팀원이 디스코드에 쓰듯 담백하게 쓴다.
- 파일 경로·엔드포인트·필드명은 백틱으로 감싼다.
